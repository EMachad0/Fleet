## When to use

Consult this doc whenever you are:

- Creating a new file (component, schema, utility, query, etc.)
- Deciding where a piece of logic belongs (route vs `$lib` vs `src/convex`)
- Moving or renaming files during refactors
- Onboarding a new feature and scaffolding its layout

## Core principle

**Distance equals reuse.**

- Used by one thing → live next to it.
- Used by two or more → promote to `$lib` or `src/convex`.
- Runs on Convex infrastructure → `src/convex`.
- When in doubt, **colocate first**. Promote on the third usage, not the first.

Do not pre-build folder hierarchies "for later".

**Domain-Driven Design (Eric Evans) governs all Convex backend design.** Naming, boundaries, and service decomposition follow DDD principles. Any deviation must be explicitly justified — explain why DDD doesn't apply and what alternative pattern is being used instead.

## Critical rules

### 1. Convex backend uses a three-layer architecture

`convex.json` declares `"functions": "src/convex/"`. `svelte.config.js` aliases `$convex` → `src/convex`. All Convex code lives here, organized into three layers:

**Root (plumbing)** — infrastructure files at the top level of `src/convex/`:
`schema.ts`, `functions.ts`, `auth.ts`, `http.ts`, `init.ts`, `auth.config.ts`, `convex.config.ts`, `test.setup.ts`

**Features (thin auth wrappers)** — subdirectories that expose public API endpoints:
`auth/`, `tenant_selection/`, `admin/tenant_dashboard/`, `admin/membership_dashboard/`

Features import and delegate to services. They handle auth context (`azQuery`, `adminMutation`, etc.) and argument validation, but contain minimal business logic. Features can nest sub-features (e.g. `admin/membership_dashboard/`).

**Services (business logic)** — `_services/<capability>/`:
`_services/auth/`, `_services/membership_lifecycle/`, `_services/tenant_provisioning/`, `_services/user_onboarding/`

Services contain pure business logic: domain rules, DB operations, and domain helpers. They export plain functions that take `ctx` and arguments — no auth wrappers, no Convex function registration. Services are named by business capability (DDD ubiquitous language), not by model or table name.

Services can freely import other services, including composing DB operations. Service boundaries are independent from API feature boundaries — a feature may wire together multiple services.

### 2. `_` prefix convention

Directories prefixed with `_` are excluded from the Convex public API but included in the convex-test module graph:

| Directory      | Purpose                                          |
| -------------- | ------------------------------------------------ |
| `_services/`   | Business logic, domain rules                     |
| `_components/` | Third-party Convex components (e.g. better-auth) |
| `_testing/`    | Internal convex-test helpers                     |

### 3. All client library code lives in `src/lib/`, imported as `$lib/...`

Don't create `src/components/`, `src/utils/`, `src/stores/`, etc. — all library code goes under `src/lib/`.

### 4. shadcn in `$lib/components/ui/`; your composites in `$lib/components/app/`

`ui/` is CLI-managed (shadcn). `app/` is hand-written. Never mix them.

### 4a. Folder-per-component, with a local `index.ts` — always

Every component lives in its own kebab-case folder. The folder contains `.svelte` file(s) plus an `index.ts` that re-exports. This applies to shadcn primitives, `$lib/components/app/` composites, and route-local components.

**Single-component folder:**

```
user-menu/
  user-menu.svelte
  index.ts          # export { default as UserMenu } from './user-menu.svelte';
```

**Multi-file folder (shadcn Dialog pattern):**

```
dialog/
  dialog.svelte
  dialog-content.svelte
  index.ts          # import Root from './dialog.svelte'; export { Root, Root as Dialog, ... }
```

Consumers import from the folder: `import { UserMenu } from '$lib/components/app/user-menu'`

Don't create flat `.svelte` files outside folders (e.g. `$lib/components/app/UserMenu.svelte`).

### 4b. No barrel `index.ts` at `components/`, `ui/`, or `app/` level

Don't create `$lib/components/index.ts`, `$lib/components/ui/index.ts`, or `$lib/components/app/index.ts`. Upper-level barrels cause circular imports, worse tree-shaking, and noisy diffs. Only per-component `index.ts` files exist.

### 5. Business logic placement

| Logic kind                               | Location                             |
| ---------------------------------------- | ------------------------------------ |
| Infrastructure (schema, auth, builders)  | `src/convex/` (root)                 |
| Business logic (domain rules, DB ops)    | `src/convex/_services/<capability>/` |
| Auth-wrapped API endpoints               | `src/convex/<feature>/`              |
| Zod schemas (shared)                     | `src/convex/schemas/`                |
| Route-specific load + form actions       | `src/routes/<path>/+page.server.ts`  |
| Route-only components                    | `src/routes/<path>/components/`      |
| Route-local Zod schema                   | `src/routes/<path>/schemas.ts`       |
| Reusable types                           | `$lib/types/`                        |
| Pure utilities                           | `$lib/utils/`                        |
| Server-only helpers (secrets, node APIs) | `$lib/server/`                       |

Don't build a `$lib/server/` service layer wrapping Convex mutations — put the logic in `src/convex/_services/`.

### 6. Use `$lib/server/` for anything that must never reach the client bundle

SvelteKit refuses to bundle `$lib/server/` into client code. With Convex, this stays small — use it only for secrets in `hooks.server.ts` / `+page.server.ts`, Node-only libraries, or auth glue outside Convex.

### 7. Route colocation — promote to `$lib` on third reuse, not first

Start route-specific. Promote the entire folder to `$lib/components/app/` only when a third consumer materialises.

Don't colocate route-only components in `$lib/components/` "just in case" — that is premature abstraction.

### 8. Zod schema placement

All shared Zod schemas live in `src/convex/schemas/` — the single source of truth for both Convex and client code.

| Side   | Import path                    | Example                                               |
| ------ | ------------------------------ | ----------------------------------------------------- |
| Convex | relative `./schemas/<name>`    | `import { roleSchema } from './schemas/tenant'`       |
| Client | alias `$convex/schemas/<name>` | `import { roleSchema } from '$convex/schemas/tenant'` |

**`import type` vs runtime import:** Convex code can `import type` from outside `src/convex/` (erased at compile time, never shipped to the backend). Runtime value imports must stay within `src/convex/`. Since schemas live in `src/convex/schemas/`, both type and runtime imports work from either side.

**Route-local schemas:** A Zod schema used by exactly one route and with no Convex relevance can live as `src/routes/<path>/schemas.ts`. Promote to `src/convex/schemas/` when a Convex function or a second consumer needs it.

Don't duplicate a Zod schema in a route and a `z.*` validator in `src/convex/` for the same shape — import from `src/convex/schemas/` on both sides.

### 9. File and directory naming

| Context                 | Convention                  | Example                                      |
| ----------------------- | --------------------------- | -------------------------------------------- |
| Convex directories      | snake_case                  | `membership_lifecycle/`, `tenant_dashboard/` |
| Convex files            | snake_case                  | `current_user.ts`, `landing_resolver.ts`     |
| SvelteKit directories   | kebab-case                  | `user-menu/`, `select-tenant/`               |
| SvelteKit files         | kebab-case                  | `create-form.ts`, `auth-client.ts`           |
| Component folder        | kebab-case                  | `user-menu/`, `button/`                      |
| Svelte component files  | kebab-case (matches folder) | `user-menu.svelte`                           |
| Component binding       | PascalCase via `index.ts`   | `import { UserMenu } from '...'`             |
| SvelteKit special files | `+prefix` lowercase         | `+page.server.ts`                            |
| Rune state modules      | kebab-case + `.svelte.ts`   | `preferences.svelte.ts`                      |
| Route folders           | kebab-case                  | `org-settings/`                              |

**Why the split:** Convex generates API paths from directory names (e.g. `api.tenant_selection.memberships`), and snake_case is the idiomatic convention for Convex function paths. SvelteKit uses kebab-case for URLs and file conventions.

### 10. Test placement

`tests/` mirrors `src/` — a test for `src/convex/init.ts` lives at `tests/convex/init.test.ts`, a test for `src/routes/auth/login/` lives at `tests/routes/auth/login/login.spec.ts`, and so on.

| Test kind                                  | Location                                               |
| ------------------------------------------ | ------------------------------------------------------ |
| Unit / integration tests                   | `tests/` mirroring `src/` path (`.test.ts`)            |
| E2E tests                                  | `tests/` mirroring `src/` path (`.spec.ts`)            |
| Internal convex-test helpers               | `src/convex/_testing/` (excluded from public API)      |
| Public test-only mutations (IS_TEST guard) | `src/convex/test_helpers/` (must be publicly callable) |

`_testing/` vs `test_helpers/`: `_testing/` contains internal queries/mutations excluded from the public API. `test_helpers/` contains public mutations that tests call through the Convex client — they need to be discoverable as `api.test_helpers.*` but are guarded by `IS_TEST` to prevent production use.

## Decision flowchart

1. **Runs on Convex?**
   - a. **Infrastructure/plumbing** (schema, auth config, function builders)? → root of `src/convex/`. Stop.
   - b. **Business logic** (domain rules, DB operations, pure domain helpers)? → `src/convex/_services/<capability>/`. Stop.
   - c. **Thin auth wrapper** exposing an API endpoint? → `src/convex/<feature>/`. Stop.
   - d. **Zod schema?** → `src/convex/schemas/`. Stop.
2. **Imports a secret or Node-only API?** → `$lib/server/<name>.ts`. Stop.
3. **Used by exactly one route?** → colocate in `src/routes/<path>/`. Stop.
4. **Svelte component?** → shadcn: `ui/<kebab>/`. Yours: `app/<kebab>/`. Always a folder.
5. **Zod schema (route-local, no Convex)?** → route-local `schemas.ts`.
6. **Pure utility or type?** → `$lib/{utils,types}/`.
7. **Anything else?** → `$lib/<category>/`.

## Patterns

- **Entity ownership:** one service per business capability, one feature per API boundary, one shared Zod schema per entity in `src/convex/schemas/`. Parallel naming makes grep-driven navigation trivial.
- **Generated code:** never hand-edit `src/convex/_generated/`. Regenerate via `bun x convex@latest dev`.
